# 2026-11-24 Docker 메모리 줄이기(32 GB PC 기준)
- 관련: `compose.yaml`(postgres `mem_limit: 3g`, 워커 `--max-tasks-per-child=50`), [팀원 PC 재현](../TEAM_SETUP.md) 1절 "Docker 메모리", PC의 `%UserProfile%\.wslconfig`(저장소 밖, 문서에 권장값)
- 계기: 사용자가 다른 과제와 함께 돌리는데 Docker 메모리 점유가 너무 크다고 함. "보편적으로는 32기가 정도"에 맞춰 달라고 함

## 왜
- Docker Desktop(WSL2)은 `.wslconfig`가 없으면 PC 메모리의 절반까지 쓴다(이 PC 30 GB 한도). 한 번 잡은 메모리를 윈도우에 바로 돌려주지 않는다
- 컨테이너별로 재 보니 크게 잡힌 몫은 postgres였고, 그 대부분은 DB 파일 캐시였다(첫 지역 조회 때 21 GB). postgres 프로세스 자체는 공유 버퍼 128 MB. 캐시는 한도를 걸면 줄어들 뿐 오류가 나지 않는다
- 워커 자식 프로세스는 한 번 커지면(관측 434 · 314 MB) 계속 그 크기를 잡고 있었다

## 무엇을 바꿨나 (비포 → 애프터)
| 항목 | 비포 | 애프터 | 근거 |
|---|---|---|---|
| WSL VM 한도 | 없음(30 GB) | `.wslconfig` `memory=8GB`, `swap=8GB`, `autoMemoryReclaim=gradual` | 컨테이너별 관측 최대 합에 여유 |
| postgres | 한도 없음 | `mem_limit: 3g` | 넘는 몫은 캐시 |
| 워커 | 자식 프로세스 계속 사용 | 작업 50개마다 새로 띄움 | 커진 메모리를 놓게 함 |

## 숫자 (같은 무거운 계산: 지역 3곳 계획 평가 + 대시보드 2곳, 1~2초마다 `docker stats`)
| 컨테이너 | 비포 최대 | 애프터 최대 |
|---|---|---|
| postgres | 21 GB | 2.7 GB |
| api | 2.5 GB | 1.3 GB |
| 워커 | 0.94 GB | 0.22 GB |
| 팀 모델 | 0.14 GB | 1.3 GB(팀 모델 비교 시험이 함께 돌던 첫 측정 2.1 GB) |
| VM 전체 한도 | 30 GB | 8.3 GB(`docker info`) |

- 계산 결과는 같음: 전주 1,633.7 t/년 · 변화 모델 +2,748 t(942~4,661), 수원 1,697.7 t/년 · +2,347.2 t. 저장값과 다른 칸 38개는 api 다시 짓기 때 확인한 것과 같은 종류(근거 표 건수 56→58, 연도별 기상 HDD · CDD)
- 첫 조회 시간(api 캐시가 빈 상태): 전주 28.1 → 31.3초, 수원 23.8 → 35.6초, 장수 9.9 → 14.9초, 대시보드 11740 12.2 → 7.5초. 애프터는 WSL을 다시 시작한 직후라 DB 캐시도 비어 있었다. 그래서 한도 때문인지 빈 캐시 때문인지는 나누지 못함. 두 번째 조회부터는 api 캐시를 씀
- 09:05 기상 수집 예약 80건(`prepare_region`)은 워커를 다시 띄운 뒤에도 새 워커가 쥐고 있음(redis unacked 시각 > 워커 시작 시각)

## 결정
- 사용자: 지금 바로 적용("지금 진행하면 안되나?"), 32 GB PC 기준으로

## 하지 않은 것 · 보류한 것과 이유
- postgres `shared_buffers` · api 캐시 크기 조정: 첫 측정에서 큰 몫이 아니었음
- 팀 모델 한도: 최대 2.1 GB, 한도를 걸면 예측이 멈출 수 있어 두지 않음. 넘치면 swap이 받음
