# 2026-11-24 도일 다시 계산은 도일 규칙이 바뀔 때만 · 원본 없는 달은 NULL · 지역 ASOS 도일 점검
- 관련: `backend/app/standard.py`(`apply_standard`, `applied_degree_day_rule`, `recompute_degree_days`, `_recompute_region_degree_days`, 새 점검 `region_asos_degree_days_item`), 시험 `tests/test_standard.py`, [기준 문서](../DATA_STANDARD.md) 5.10 · 판 1.59
- 계기: 상태 점검(11-24)의 B1 "도일 다시 계산의 남은 구멍"(사용자 "B1부터 진행"). 앞선 기록: [도일 다시 계산 고침 #103](2026-11-24-degree-days-recompute-asos.md), [12곳 되돌림 #105](2026-11-24-restore-asos-degree-days.md)

## 왜
- 11-20 덮어쓰기(손정리 12곳 ASOS 1,475개월이 ERA5 도일로)는 **도일과 상관없는 판 올림**(1.3, K-apt 규칙) 때 일어났다. `apply_standard`가 판이 바뀔 때마다 도일까지 다시 계산했기 때문이다. #103은 ASOS 달을 ASOS 원본으로 계산하게 고쳤지만, 다른 이유의 판 올림에도 도일 전체를 다시 계산하는 구조는 남아 있었다
- 원본이 없는 달의 처리가 셋으로 갈렸다: 전주 대체 달 · 지역 대체 달은 CDD만 지우고 HDD는 옛 값 유지(10월 냉방 기준온도 변경 때의 처리), 지역 ASOS 달은 그대로 유지(#103). 다시 계산은 규칙이 바뀔 때 의미가 있는데, 그때 옛 값을 남기면 옛 규칙 값과 새 규칙 값이 섞인다
- 11-20 일은 나흘 동안 아무 점검에도 걸리지 않았다(기준 점검의 도일 항목은 전주 ASOS만 대조)

## 정한 규칙 (고치기 전에 적음)
1. 도일 규칙(`degree_days.RULE`, 지금 "HDD 18°C · CDD 24°C")이 마지막 적용 때(`data/ops/standard.json`의 `rule`)와 같으면 도일은 다시 계산하지 않고 저장값을 둔다. 표식이 없을 때(처음)와 규칙이 바뀌었을 때만 다시 계산한다
2. 다시 계산은 달마다 그 값의 원본으로(전주 ASOS = 저장된 일자료, 지역 ASOS = 그 지점 일자료 원본, 대체 = ERA5-Land 원본). 원본이 없거나 그달이 다 차지 않으면 HDD · CDD 둘 다 NULL로 두고 센다
3. 기준 점검에 '지역 기상 ASOS 달의 도일 = 그 지점 일자료로 다시 낸 값' 항목을 더한다(다르면 FAIL, 원본이 없는 달은 따로 셈)

## 바뀐 것 (전 → 후)
| 경우 | 전 | 후 |
|---|---|---|
| 판이 다른 까닭으로 오름(도일 규칙 그대로) | 도일 전부 다시 계산 | 다시 계산 안 함, 저장값 유지(`{"skipped": …}`) |
| 규칙이 바뀌었고 전주 · 지역 대체 달의 원본 없음 | CDD만 NULL, HDD 옛 값 | HDD · CDD 둘 다 NULL |
| 규칙이 바뀌었고 지역 ASOS 달의 원본 없음 | 저장값 그대로 | HDD · CDD 둘 다 NULL |
| 기준 점검 | 전주 ASOS 달만 대조 | + 지역 ASOS 달 전체 대조 |
