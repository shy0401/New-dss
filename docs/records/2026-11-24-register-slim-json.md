# 2026-11-24 건축물대장 속성은 쓰는 키만 읽기: 지역 첫 분석의 순간 최대 1,535 → 580 MB
- 관련: `backend/app/official.py`(`register_attributes`, `REGISTER_AREA_KEYS`), `area.py`(지역 분석 입력), `register_grid.py`(지도의 건축물대장 요약), `energy_parcels.py`(지번별 연면적). 앞 기록: [팀 변화 모델 저장](2026-11-24-team-model-cache.md)
- 계기: 사용자 — 남은 메모리 항목을 현재 상태를 백업해 두고 진행, 결과가 바뀌면 되돌리는 방식으로. 그 두 번째 항목(api 계산 중 순간 최대)

## 원인 찾기
- api 컨테이너 안 별도 프로세스에서 전주(52110) 첫 계획 평가를 메모리 추적하며 돌림: 순간 최대 1,065 MB(파이썬 몫) 중 **770 MB가 JSON 풀기**(`json/decoder.py`), 추적 8단계 · 40단계 모두 psycopg · SQLAlchemy 안쪽만 잡힘 → DB의 JSON 칸을 행째 읽는 쿼리
- 코드에서 찾음: 지역 분석 입력이 건축물대장의 `attributes`(JSON, 건물 한 동의 표제부 전체)를 지역 칸의 모든 동에 대해 읽고, 그중 연면적 계산 키 5개와 용도만 씀. 전주 70,735동, 저장 47 MB(동당 0.7 KB) → 파이썬 사전으로 약 10 KB씩 = 측정된 770 MB와 같은 크기
- 같은 패턴이 두 곳 더: 지도의 건축물대장 요약(용도 · 에너지 등급 추가), 지번별 연면적(연면적 키만)

## 무엇을 바꿨나
- `register_attributes(db, *extra)`: PostgreSQL에서는 `json_build_object('키', attributes->'키', ...)`로 쓰는 키만 SQL에서 만들어 받음. 키가 없으면 어느 쪽이든 None. 그 밖의 DB(SQLite 시험)는 예전처럼 칸 전체
- 세 쿼리가 이 칸을 씀. 계산 코드(`register_areas` 등)는 그대로

## 백업과 판단 규칙 (바꾸기 전에 정함, 팀 모델 저장과 같은 규칙)
- 백업: main 그대로(새 브랜치), 이미지 `carbon-urban-dss-api:before-peak-2026-11-24`
- 규칙: 시각 기록 칸만 빼고 모든 칸이 같음 + 시험 통과 + 첫 조회가 기준보다 느리지 않음. 어긋나면 되돌림
